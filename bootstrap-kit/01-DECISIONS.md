## D1 为什么 SOP 必须与 `codebuddy-eco/` 同级

- 数据：审查侧实测「SOP 与 codebuddy-eco 同级 = True」；包内 6 处 `../SOP` 指针
  （README、governance、registry、docs.paths、机检脚本、SOP 各一；行号随编辑漂移，
  以 `grep -rn '\.\./CodeBuddy' codebuddy-eco/` 实时核对为准，不在此写死）。
- 决策：交接包把二者作为**一对同级条目**整体搬运；机检 `--sop` 也走 `../` 相对路径。
- 后果：只搬目录不搬 SOP → 6 处指针全断、`--sop` 失效，正是 M5 要防的「改一处没带动指针」。
- 指针：SOP 20.11（口径统一正式条款）、`verify/terminology_check.py` 的 `ROOT` 定义。

## D2 为什么技能全放 `.codebuddy/skills/` 而不是顶层自建 `skills/`

- 数据：SOP 第 19 章实测诊断——旧生态把规则放顶层 `rules/`、押 4 个 hook 事件，
  手机/云端任务**钩子不跑**，23 条规则 + 4 技能几乎全休眠。
- 决策：新生态四个技能直接住官方自动加载路径 `.codebuddy/skills/<name>/SKILL.md`，
  放对目录即被宿主读取并语义触发，**不需薄壳、不需脚本、不押钩子**。
- 指针：SOP 19（强制链与通道失效）、20.0–20.6（接活）、README.md 第二节。

## D3 为什么用户级基座是「模板 + 安装」两步，而不是直接放规则目录

- 数据：审查侧实测 `~/.codebuddy/rules/` **不存在**；`base/rules/core-8.md` 为 8 条铁律模板
  （字节/行数随口径订正微调，以 `wc` 实时核对为准，不在此写死）；
  MANIFEST 里 `rules.user_base.install_to = "~/.codebuddy/rules/core-8.md"`。
- 决策：`base/rules/core-8.md` 是**可 clone 的模板**（本机用户级目录带不走、沙箱里也不是真机），
  落地时须 `mkdir -p` + `cp` 装到用户级，才跨项目常驻生效。
- 后果：漏了这一步，8 条铁律与元规则在跨项目时全不生效；这是最容易漏的一步。
- 指针：README.md 第六节、SOP 20.9（三分离第①格）、`docs/base-rule-mapping.md`。

## D4 为什么规则按三分离，不照搬冷热分层

- 数据：旧生态 `rules/core.json` 23 条 + `index.json` 280KB + `registry.json` 325KB，
  23 条共用 49 个字段、描述散落 6 处；MANIFEST 里 `rules._layers` 已写明弃用 hot/warm/cold。
- 决策：改官方「作用域 × 触发 × 强制力」三维度——
  用户级常驻（`core-8.md`，`alwaysApply:true`）、项目级常驻（`zh-style.md`，`alwaysApply:true`）、
  项目级条件（`docs.paths.md`，`alwaysApply:false` + `paths:["docs/**/*.md"]`）、
  治理台账（`docs/rule-ledger.md`，不进 context）。
- 后果：只有无条件铁律常驻，情境契约命中才注入，台账不占 context——正对 20.7 防卡顿。
- 指针：SOP 20.9、`.codebuddy/MANIFEST.json` 的 rules 段（5 格）、README.md 第六节。

## D5 为什么 `description` 不堆触发词

- 数据：4 技能 `description` 实测 54 / 62 / 76 / 90 字，斜杠数均为 0；
  触发词唯一真源在正文「何时使用」（4/4 带「触发词（唯一真源）」标记）。
- 决策：官方 Skills 口径里 `name`/`description`/`allowed-tools` 均标「必填：否」，
  `description` 是「帮助 AI 理解何时使用」的一句话能力描述，触发靠 AI 语义识别，
  不靠 `/` 分隔的关键词清单。「三字段写齐」诚实定为**本生态约定**，不冒充官方必填。
- 后果：20.8 曾声称整改却没落地，20.12 补做并固化进机检第 ⑦ 项——
  **规范化只有变成门禁才不退化**。
- 指针：SOP 20.8 / 20.12、`docs/registry.md` 的 `skill_contract` 机读区。

## D6 为什么验收靠机检 8 项 + 三态，而不是「我说全绿」

- 数据：本沙箱真跑三模式 → 默认/strict 扫 13 个 .md、`--sop` 扫 14 个 .md（含 SOP），
  引用处数随正文增长（判据不看固定值，看真跑输出）；三模式均 PASS 8 / WARN 0 / FAIL 0、
  **0 断链 / 退出码 0**（历次落地当次快照数字见 D8 ③ / D9 ② / D10 ②，均保留作留痕、不作判据）。
  `--json` 输出同一套结果、判据不变。
  8 项 = 真源齐备(15/15) / 词表 / 编号(B-01..B-08) / §引用断链 / 铁律复制(M2) / MANIFEST(5格) / 技能契约 / **规则契约**（官方 Memory 文档三控制字段，SOP 20.12.2）。
- 决策：判据 = **真实退出码 0**，不是任何人的口头结论；配置唯一真源是 `docs/registry.md`
  第七节机读区，机检脚本不硬编码第二份（否则检查器自己制造口径冗余）。
- 后果：L1 全绿只证明**包自洽**；「另一会话加载后真跑通」是 L2/L3，审查侧认 UNKNOWN。
- 指针：SOP 20.10 / 20.11 / 20.12、`verify/terminology_check.py`、`docs/registry.md`。

## D7 为什么不押钩子 / 不宣称 `machine-bootstrap --verify`

  当前 git 状态见 **D8**（本体已本地 init、0 remote；该结论不受影响）。
- 决策：按官方统一口径**直接定该能力不存在**——删掉脚本里的 `--verify`、`README` 冷启动第 4 步、
  governance 验证清单、三通道校验的宣称，改为「三通道就位用 L2 三态实测确认」；
  不再写「占位/待补」这种悬空承诺。
